# P4l 5% MAC 预算下 width=16 路由：训练前停止

P4l 不搜索多个宽度，而是按静态规则选择：在已审计的宽度集合中，取总 MAC 相对共享 MLCNN 增幅不超过 5% 的最大宽度。width=16 的 MAC 增幅为 4.996%，width=20 超出预算，因此事前唯一选择 w16。

CUDA Graph 成本审计显示：

- 参数量增加 0.340%，MAC 增加 4.996%；
- eager 与 Graph 输出完全一致；
- batch=1 Graph 中位延迟仅比共享 Graph 增加 4.39%，P95 增加 3.05%；
- batch=64 吞吐为 20,751 samples/s，保留共享 Graph 的 84.34%。

预注册要求 batch=64 吞吐至少保留 85%，因此 P4l 失败并在数据生成、训练前停止。差距只有 0.66 个百分点也不能事后修改门槛。

P4k 与 P4l 联合揭示了宽度压缩的不可兼得区间：w4 成本合格但精度显著失败；w16 低延迟和 MAC 合格，但批吞吐略低于门槛。继续试 w12/w20 会演变为结果导向的宽度搜索，不能形成可靠创新。

下一步应改变结构，而不是继续缩放独立第二骨干：共享 MLCNN 的浅层时序特征图，在参数路径中保留未池化序列并使用轻量 grouped temporal continuation。该机制既避免重复早期卷积，又不同于已失败的全局池化浅层安全头。
